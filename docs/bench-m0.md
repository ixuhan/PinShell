# M0 基准实测

> 机器：Windows 11 + pwsh 7.6.6 + WebView2 157 + Tauri 2.12.5 + xterm.js 6.0.0（WebGL on）
> 时间：2026-11-16 20:23，`tauri dev`，debug 构建（未优化，release 会更快）
> 复现：`npm run app:dev`，前端启动 1.5 秒后自动跑基准并把结果打到 stdout（`[bench]` 行）

## 数字

| 指标 | 实测 | 说明 |
|---|---|---|
| 前端就绪（模块求值 → 可发 spawn） | 24 ms | Vite dev server + xterm 初始化 |
| spawn 调用（IPC 往返 + ConPTY 创建 + 进程启动） | 42 ms | 不含 Shell 自己初始化 |
| 首个字节到达 | 21 ms | ⚠️ **不是**「可输入」，见下 |
| IPC 往返 p50 / p99（300 次空命令） | 1.8 / 4.3 ms | 峰值出现在首轮，后续稳定在 1.8ms |
| 1MB 文本一次性写入渲染 | 53–59 ms | 约 17–19 MB/s |
| WebGL | 启用成功 | — |

三次运行的趋势：IPC p50 3.3 → 2.3 → 1.8ms，p99 7.5 → 7.1 → 4.3ms（JIT 与 IPC 通道预热后收敛）。

## 两个必须说清楚的坑

### 1. 「首个字节」不等于「提示符就绪」

ConPTY 在创建后会立即吐一些控制序列（光标、屏幕状态），所以首字节 21ms 是**下限**，不是用户能敲命令的时间。真实的「可输入」由 Shell 自己的初始化决定：

- `cmd.exe`：约 35 ms（此前用独立进程实测）
- `pwsh`：约 730 ms（此前实测 6 次，726–793 ms）

所以用户感知的启动时间 ≈ `max(框架 ~90ms, Shell 初始化)`。用 pwsh 时是 **730ms 量级**，用 cmd 时是 **~100ms**，而框架只贡献了几十毫秒。

正确的测法要等 M1 的集成脚本：收到 OSC 133 `A` 的那一刻才是提示符就绪。M0 暂用「首个字节」占位，会在 M1 替换掉。

**M1 已替换**：`src/main.ts` 在首个 `prompt_ready` 时打一行 `[bench] input-ready <ms>ms (module eval -> OSC 133 A)`，HUD 同时显示「可输入 <ms>ms」。新的数字等下次 release 手工运行补进本文。

### 2. IPC 往返不是 0.1ms 量级

此前估算「0.1–0.3ms」是错的，实测 p50 ≈ 1.8ms，p99 ≈ 4.3ms（WebView2 postMessage + Tauri 派发 + 序列化）。

后果：

- **逐键 `await invoke` 是危险的**。一帧只有 16.7ms，一秒钟的连续输入会排队。所有按键路径必须是「先本地回显、再异步写 PTY」，且不能 `await`。
- **Ghost Text 必须走前端只读热缓存**。40ms 防抖后再跨 IPC 查询，等于每个停顿多 2ms；在历史里做模糊匹配本身也要几毫秒，合起来会破坏「打字跟手」。
- 高频流（PTY 输出）可以换成 `tauri::ipc::Channel` 而不是事件，代价更低——留到 M1 评估。

## 对照红线

| 红线 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 冷启动到可输入 | < 1.5s | 框架 90ms + shell ≈730ms（pwsh） | ✅ 通过 |
| 按键端到端 p99 | < 10ms | 本地回显未测；IPC 单次 p99 4.3ms | ⚠️ 待 M1 测完整链路 |
| 1MB 输出渲染 | ≥ 30 fps（≤33ms） | 53ms | ❌ 未达标 |

1MB 未达标的原因与对策：一次性 `term.write(1MB)` 是最坏情况（无分帧）。M1 要加 16ms 帧聚合，把「按帧写入」替换「来一块写一块」，然后再测。若仍不达标，再考虑降级策略（限制回滚行数、关闭 ligature、必要时切 DOM 渲染对照）。

## 结论

Tauri 这条链路在**启动**上完全够用（框架开销被 Shell 自己掩盖），在**交互**上需要两条纪律：本地回显不阻塞、输出按帧批量写。真正的风险不是 Tauri，是「每键都跨进程 + 每块输出都立刻画」这种写法。
