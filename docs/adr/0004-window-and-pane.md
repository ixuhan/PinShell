# 0004 窗口是视图，会话是数据；拼接 = 分格

- 状态：已接受（2026-11-16）
- 相关：ADR 0001、GLOSSARY「会话」「窗口」「分格」

## 背景

需求要「多窗口拼接」，并且明确要求**任意会话都能拼**，包括终端与串口混拼。这带来一个必须先回答的问题：窗口和会话是什么关系？

## 决策

1. **窗口是视图容器，会话是数据。** 一个会话同一时刻只能挂在一个窗口的某个分格里——不是限制，而是因为输入所有权、串口独占、CWD 跟随都是「一个会话一份」。复制会话会让两个输入条抢同一份输出。
2. **拼接 = 窗口内的分格树。** 一个窗口由二分布局树组成，每个叶节点是一个分格，每个分格挂一个会话。分格可横切、竖切、任意嵌套，但限制最大嵌套 3 层（超过就退化成「拖出去开新窗口」，否则每格小到不可用）。
3. **分格不区分通道类型。** 终端与串口在分格里完全同权：各自有自己的标题、状态点、输入条、时间戳开关。这是 ADR 0001 的直接收益。
4. **跨窗口只做吸附记位置，不做窗口融合。** 把会话拖出成独立 OS 窗口后，窗口之间可以有「组」的概念：记住相对位置与对齐边，还原时按原样摆回。**不**把两个 OS 窗口合成为一个真实窗口——自绘窗口融合要跟 DWM、DPI 迁移、多显示器缩放打架，收益远小于成本。
5. **窗口级 UI 跟随焦点分格**：文件面板、状态栏、命令片段条都属于窗口，永远展示**焦点分格**的会话状态；非焦点分格只有终端输出与自己的输入条。

## 数据模型

```
Workspace
├── windows[]            // 每个窗口：尺寸、位置、显示器、组 id
│   └── layout           // 二叉分格树：split(dir, ratio, childA, childB) | leaf(session_id)
└── sessions[]           // 与窗口无关的会话集合（含冷会话）

Group(可选)              // 跨窗口吸附：members[]、anchor、相对偏移
```

## 后果

- `workspace.json` 从「单窗口」升级为「窗口组」，越早改越便宜——这也是现在定下来的原因。
- 还原顺序有依赖：先建窗口与分格树，再按 session_id 拉起热会话、回放卷轴；冷会话只还原格子里的占位。
- 分格为空的窗口不允许存在（最后一个分格关闭时整个窗口关闭），避免出现空壳窗口。
- 串口会话被拖到另一个窗口时，端口不重开、不中断——迁移的是视图，不是通道。这是「窗口是视图」这条决策最有价值的体现。
- 跨窗口拖动时若目标分格已有会话，行为是**交换**而不是替换（替换会悄悄关掉一个会话，代价太高）。

## 替代方案

- **窗口 = 会话（一窗一会话）**：最简单，但用户要并排看终端与串口时必须靠操作系统窗口管理，做不到吸附还原。
- **标签页 + 分栏两套并存**：能力最强，但输入条归属、焦点、快捷键会立刻长出两套语义，第一版扛不住。
- **真正融合多个 OS 窗口**：体验上限最高，实现成本与稳定性风险都不可接受。
